# Library index — grouped by problem shape, not by source project

Hand-built 2026-09-08, from the 39 entries mined from click, requests,
werkzeug and starlette. Not generated by a script — read and grouped by
actually judging what each problem is, the same discipline used to reject the
two earlier "looked like a match" pairings that turned out to be wrong.

**What this is for:** when checking whether a real bug has a genuine match in
the library, narrow to one group first instead of reading all 39 entries every
time. Still read the actual entry before crediting a match - a group narrows
the search, it does not replace judgement.

**Group 6 is the weakest.** It is nine entries wide because "assumed it would
always be there" is really several different failures wearing one label. Treat
a group-6 hit as a starting point to verify, not a match on its own.

## Maintaining this

New entries from future mining need a group added by hand, same as this file
was built - reading the problem, not running a keyword match. If a new
entry does not fit any group above cleanly, that is worth noticing: it might
be the first of a tenth group, or it might belong in 6 by default, which is
itself a signal the mining is drifting into territory this list doesn't cover
yet.
